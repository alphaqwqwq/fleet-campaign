# Master、Plan、Exec、Review 与 Agent 工作流

## 文档角色与状态事实

- Master 维护唯一跨 Plan 路线图、阶段门槛、活动租约和下一动作，不实现应用代码。
- Plan 负责裁决长期边界、数据契约、兼容和风险；Exec 只能在已裁决边界内实施。
- Exec 是一个可独立构建、验证、提交和回滚的工作单元；Review 独立检查其范围、证据和遗留风险，不实施功能。
- 文档路径保持稳定，以文件头状态表达生命周期；架构、状态和结果记录只能写已发生、已验证的事实。
- 设计假设、计划目标、待用户决定项、未验证项和失败项必须显式标记，不得混入已完成事实。

纯自动推进还必须遵守 [自动化工作流](AUTOMATION-WORKFLOW.md)。文档与 Git/GitHub 是状态真源，会话只是可替换执行器。

## 新对话与短提示词

每个 Master、Plan、Exec 或 Review 都先有一个仓库内的目标文档。新对话的用户提示词必须很短，只负责定位，不重复文档内容：

```text
<ROLE>|<TARGET>+<CHAT-NN>+<SHORT-GOAL>
角色：<MASTER / PLAN / EXEC / REVIEW / BROWSER>。目标文档：<绝对路径>。
先阅读该文档列出的必读材料和本工作流；遵守文档内硬约束，不执行其范围外操作。
```

- 标题和序号遵守 [会话命名约定](../../.opencode/SESSION-NAMING.md)。
- 目标文档是稳定的上下文锚点：它必须自行包含背景、已确认事实、必读文件、约束、目标、非目标、验收和止损条件。
- Agent 首答必须复述标题、角色和目标文档绝对路径，说明已读取的材料；之后以目标文档为准，而非依赖长提示词中的临时上下文。
- Plan/Review 对话可以调查和裁决；Exec 对话不得以“自行研究并完成”为由扩大范围。

## Master 的职责

- 只根据路线图、目标文档、Git、PR、CI、部署和用户决定更新状态。
- 使用普通会话调度有界子任务；Master 本身不使用覆盖整个 Plan 的 Goal Mode。
- 角色 Agent 释放单写者租约后，普通 Master 编排层集中执行提交、推送、PR、Review 报告入库和安全回收；只有依赖、固定门禁、独立 Review `pass`、PR checks 和结果记录均满足后才合并。
- 发生契约变化、不可逆外部操作、凭据边界或最终人工体验 Gate 时暂停并请求用户。

## Plan 的职责

Plan 是实施前的范围合同。只有状态为 `Approved` 的 Plan 才能创建 Exec。每个 Plan 必须写明：当前基线、目标、非目标、依赖、设计裁决、模块边界、数据与协议影响、验收、风险、回滚、止损条件和 Exec 拆分。

## Exec 与 Review 的职责

Exec 必须写明允许/禁止文件范围、完成条件、自动化验证、人工验收、提交/回滚和结果记录。Review 必须写明审查输入、固定 head、证据、问题级别、放行结论、遗留风险和后续责任。Review 只审不修。Exec 标记 `Merged` 不等于通过 Review。

## Exec 生命周期

```text
Draft → In Progress → Verified → Pushed → Merged
```

- `Draft`：范围、文件边界和验证清单完整。
- `In Progress`：仅在对应 feature 分支修改。
- `Verified`：所有必需自动化和手动验证完成，结果写入 Exec。
- `Pushed`：有对应提交哈希并已推送 GitHub。
- `Merged`：通过 PR 合入 `main`，记录合并提交和部署结果。

## 每次执行必须遵守

1. 先阅读关联 Plan、已有规则约束、ADR、最近相关 Exec 和目标文档规定的材料。
2. 只修改 Exec 列出的文件；新增文件必须记录用途。
3. 不得以删除、跳过或弱化既有断言换取通过。
4. 完成后按 Exec 清单验证；失败要保留真实证据。
5. 更新 Exec 的结果记录，提交并推送；未验证的变更不得标记完成。
6. 每份活动 Exec/Review 固定记录 `状态 / 下一动作 / 证据 / 基线`，作为跨会话交接。

## 文档与提示词生成约束

- 新文档必须属于 `docs/README.md` 的目录，并从索引、关联 Plan 或 Exec 可发现；不因完成而移动或改名。
- Plan、Exec、Review 的硬约束写入各自目标文档，不放在临时对话长提示词中。
- 文档避免复制大段代码或重复事实；使用文件路径、提交哈希、测试命令、事件 ID、部署 URL 等可追溯证据。
- 规则文档必须写清实体、前置条件、状态转换、不变量、错误处理和验证方式；不得只写愿景。
- 开发提示词只保留按角色复用的通用模板，不为每个 Exec 复制文件；运行时 LLM 提示词另行版本化，不能和开发提示词混用。
- 运行时 LLM 模板必须有稳定 ID、版本、Hook、输入事实、可见性、禁止断言、输出 Schema 和降级文本；模型输出不得改写规则状态。

## 止损条件

出现未裁决的存档迁移、事件协议、随机数、房主权威、LLM 边界、跨包所有权、发布域名或外部权限变化时，停止扩展当前 Exec 并回到 Plan/Review。类型检查、lint、测试或构建任一失败，或同一问题两次后仍无可信结论时，同样停止并记录证据。
